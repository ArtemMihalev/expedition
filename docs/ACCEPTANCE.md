# Пошаговая приёмка этапа 3

Все команды ниже выполняются в PowerShell из `F:\web\expedition`. Используйте имитатор платежей. Тестовый набор сам запускает локальные HTTP-серверы, создаёт новые SQLite и учебных покупателей; `run.py`, туннель и реальные Telegram-аккаунты для него не нужны.

## Быстрый полный прогон

```powershell
cd F:\web\expedition
.\.venv\Scripts\python.exe scripts/check_warehouse.py
$LASTEXITCODE
```

Код 0 означает успешное завершение. При FAILED или ненулевом коде проверка не пройдена: сохраните текст ошибки и отчёт. Не запускайте команду с `python -O`, он отключает проверочные assert.

Отчёты каждого запуска перезаписываются:

- `docs/warehouse-report.csv`: сценарий, ожидалось, получено, статус.
- `docs/warehouse-report.json`: acceptance_id (номер 1–13), ответы, ID, база, таблицы и суммы.
- `docs/warehouse-unit.log`: регрессионные проверки, включая ошибку обычного возврата.

Для отдельного пункта добавьте `--scenario N --skip-unit`. Можно выбрать несколько: `--scenario 9 11 12 --skip-unit`. `--skip-unit` пропускает повторный запуск прежних тестов; сами выбранные приёмочные сценарии выполняются полностью. Для сдачи сохраните также отчёт полного прогона.

## Ручной стенд в Telegram

Для показа первой цепочки остановите прежний `run.py` через Ctrl+C. Прежний процесс этого же бота одновременно работать не должен.

Создайте чистую отдельную базу без товара:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_warehouse.py --db data/warehouse-tests/test-manual.db --stock 0 --buyers 20 --reset
```

Эта команда сбрасывает только указанную учебную базу. `data/shop.db` не удаляется. Не выполняйте её, пока учебный сервер использует test-manual.db.

В отдельном окне запустите прежний HTTPS-туннель на порт 8080. При необходимости:

```powershell
cloudflared tunnel --protocol http2 --url http://127.0.0.1:8080
```

Если выдан новый адрес, обновите только `MINI_APP_URL` в локальном `.env`. Не показывайте `.env` на записи. Затем в окне бота:

```powershell
$env:DATABASE_PATH = "data/warehouse-tests/test-manual.db"
$env:RESERVE_SECONDS = "120"
.\.venv\Scripts\python.exe run.py
```

Переменные действуют только в этом окне PowerShell. Менеджер открывает `/cabinet` из Telegram. Для операций покупки он может использовать свой же аккаунт. Второй аккаунт нужен для наглядного показа А/Б и доступа к чужому заказу; для автоматических конкурентных сценариев реальные аккаунты не нужны.

## 1. Ручная цепочка

1. Mini App → «Склад»: выберите рюкзак, проведите поступление 10. Зафиксируйте **10/0/10** и запись поступления.
2. В боте добавьте 3 рюкзака, оформите заказ с оплатой «Демонстрация без платёжного провайдера». Не оплачивайте пока. Обновите склад: **10/3/7**.
3. В пределах 120 секунд нажмите «Демо: успешный платёж». Обновите склад: **7/0/7**. В журнале склада — продажа, в финансовом — одно поступление.
4. Оформите новый заказ на 2 рюкзака, не оплачивайте: **7/2/5**.
5. Дождитесь его срока плюс до 5 секунд работы worker. Обновите: **7/0/7**, в журнале — истечение.
6. В Mini App → «Заказы» откройте первый оплаченный заказ → «Запросить полный возврат». После подтверждения worker обновите: **10/0/10**. В журнале — один возврат товара и одна денежная операция возврата.

Автоматический возврат может подтвердиться быстро. До подтверждения склад прежний; это состояние гарантированно проверяется автотестом. Если оплата шага 3 опоздала, начните цепочку заново на чистом учебном стенде: поздняя оплата проверяет другой сценарий.

Автоматическое воспроизведение:

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --scenario 1 --skip-unit
```

В JSON поле `actual.triples` содержит шесть требуемых состояний и дополнительное повторение 7/0/7 до подтверждения возврата.

## 2–3. Ограниченный товар и одновременные покупатели

Ожидаются 2 успеха, 28 отказов и 2/2/0. `--stock`/`--buyers` меняют №2; №3 сохраняет обязательные 10/50.

## 8. Гонки и граница срока

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --scenario 8 --skip-unit
```

В каждом из пяти прогонов выполняются две гонки: оплата/отмена до срока и оплата/освобождение ровно на сроке. Дополнительно оплата проверяется за 1 мс до, ровно на и через 1 мс после границы управляемыми часами сервера.

В JSON смотрите `actual.winner`, `actual.explanation`, reservations.state, expires_at, payments.confirmed_at и journal. До срока допустимы consumed либо cancelled с поздним денежным возвратом. На границе — expired: оплата может сама освободить просроченный резерв, даже если worker ещё не успел. Состояние consumed означает принятую продажу; cancelled/expired с подтверждёнными деньгами требуют денежного возврата. Победитель до срока зависит от порядка фиксации транзакций.

На защите запишите конкретно: «В этом прогоне победила ___; состояние ___, срок ___, время подтверждения ___. Повторного списания или освобождения нет». Значения берите из своего отчёта.

## 9. Б купил последнюю единицу, А оплатил поздно

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --scenario 9 --skip-unit
```

Стенд сам использует цену 1 200 ₽, себестоимость 700 ₽ и нулевые расходы. Не меняйте рабочий каталог. А резервирует, срок истекает; Б покупает освободившийся товар; затем приходит оплата А.

После возврата А: склад 0/0/0, два receipt по 120000 копеек, один refund 120000, cost_paid=70000, cost_returned=0, cash_flow=120000, result=50000. Повторы ничего не меняют. В проекте конфликт обозначен `orders.conflict_reason` и payment_status=refund_pending до возврата; после подтверждения — refunded. Это соответствует payment_conflict из задания, отдельного одноимённого enum нет.

До подтверждения возврата `pending_summary` показывает временное поступление; поле `error` сохраняет ошибку имитатора. Товар Б не возвращается на склад.

## 11. Авария с возвратом, ошибка, потерянный ответ

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --scenario 11 --skip-unit
```

Сервер завершается кодом 74 после фиксации позднего платежа и задания, до внешнего возврата. На восстановленном управляемом стенде последовательно воспроизводятся временная ошибка и потерянный успешный ответ. В обоих случаях задание остаётся pending с ошибкой, финансового возврата ещё нет. После включения worker он читает уже созданный результат и подтверждает один возврат. В JSON: after_crash, fault_steps, demo_provider_refunds, refunds, finance_operations. Нельзя считать потерянный ответ разрешением отправить новую операцию с другим ключом.

## 12. Авария внутри оформления

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --scenario 12 --skip-unit
```

Отдельный сервер завершается кодом 75 после записи заказа, резерва и первого товара, до второго товара и commit. После аварии в after_crash отсутствуют orders, order_items, reservations, reservation_items, payments и финансовые операции; у товаров reserved=0. Точка остановки `during_checkout` доступна только изолированному серверу с training=True. В публичном API маршрута остановки нет.

## 13. Подмена роли, владельца, суммы и срока


После ошибки остаются прежние on_hand, cost_returned=0 и refunds=0; задание не объявляется успешным. После подтверждения товар и себестоимость восстанавливаются один раз. При полном прогоне этот тест уже запускается среди регрессионных.

## Показать настоящие строки базы

В JSON найдите нужную запись по acceptance_id и путь `actual.database`. Подставьте **точное имя**, например:

```powershell
.\.venv\Scripts\python.exe scripts/inspect_finance.py --db "data/warehouse-tests/test-ИМЯ-ИЗ-ОТЧЁТА.db"
```

Это пример с заполнителем, его нужно заменить. Скрипт показывает остатки, резервы, движения, платежи, возвраты и финансовые операции. Денежные суммы в БД — копейки: 120000 означает 1 200 ₽. Исторические снимки внутри JSON фиксируют промежуточные состояния, тогда как сам SQLite-файл содержит итог сценария.

Для сохранения полного отчёта перед отдельными прогонами:

```powershell
Copy-Item docs/warehouse-report.json docs/acceptance-full.json
Copy-Item docs/warehouse-report.csv docs/acceptance-full.csv
Copy-Item docs/warehouse-unit.log docs/acceptance-full-unit.log
```

## Вернуться к прежней базе

Остановите ручной стенд Ctrl+C. В том же PowerShell удалите только переменные окружения (это не удаляет файлы):

```powershell
Remove-Item Env:DATABASE_PATH
Remove-Item Env:RESERVE_SECONDS
.\.venv\Scripts\python.exe run.py
```

Бот снова использует DATABASE_PATH из прежнего `.env`. Если до проверки эти переменные уже были заданы специально, восстановите их прежние значения вместо удаления.
