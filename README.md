# Expedition — Telegram-магазин и финансовый Mini App

Учебный магазин товаров для путешествий. Один Telegram-бот обслуживает покупателей и менеджера; бот и HTTP-сервер работают одним процессом с общей SQLite. Реальные деньги не принимаются. Существующие ID заказов сохраняются.

## Этап 3: правила склада (до изменения кода)

1. Поступление и три остатка доступны менеджеру в Mini App → «Склад». Каждое поступление сохраняет автора и ключ запроса.
2. Резерв всего заказа создаётся при подтверждении на 120 секунд. Корзина не резервирует. `products.stock` хранит on_hand, `reserved` — резерв; доступно = stock − reserved.
3. Если хотя бы одной позиции не хватает, вся транзакция откатывается, включая заказ, резерв, состав и журнал.
4. SQLite `BEGIN IMMEDIATE` сериализует записи между соединениями и процессами. Побеждает первый допустимый зафиксированный переход. Время проверяется внутри перехода; `now >= expires_at` означает истечение. Оплата потребляет резерв, отмена/истечение только освобождают его. После принятой оплаты требуется полный возврат.
5. Позднее подтверждение (даже при нажатии до срока) сохраняет одно поступление с нулевой себестоимостью и задание полного денежного возврата. Товар не продаётся и при таком возврате не прибывает. Покупатель видит «Резерв закончился, оформляется возврат».
6. Активные резервы и задания возвратов хранятся в SQLite. При запуске и каждые 5 секунд процесс освобождает просроченное и продолжает возвраты. Постоянный ключ возврата переживает ошибки и перезапуск; внешний запрос выполняется вне транзакции.

Схема: `products(stock,reserved)` → `reservation_items` → `reservations(order_id UNIQUE,state,expires_at)` → прежние `orders/order_items/payments/refunds/finance_operations`. `stock_movements` хранит дельты on_hand и reserved, заказ, автора и ключ операции. Ограничения/триггеры БД запрещают отрицательные количества и reserved > stock. Снимки цен и себестоимости прежних заказов не меняются.

План миграции: сохранить прежний свободный остаток открывающей записью журнала; прежние неоплаченные списания вернуть в on_hand и оформить срочный резерв; оплаченные/выданные продажи не списывать повторно. Новая база начинает с нуля: менеджер проводит явное поступление. Затем реализовать атомарное оформление, переходы и очередь возвратов; добавить склад в существующий кабинет; выполнить изолированные HTTP-проверки и сохранить фактический отчёт.

## Ответы на вопросы перед реализацией

1. **Где оформляют заказ и запускают оплату?** В Telegram-боте: каталог → товар → корзина → имя → самовывоз → способ оплаты → проверка → подтверждение. Тестовый счёт ЮKassa или учебные кнопки оплаты появляются в том же боте.
2. **Как сервер подтверждает и сопоставляет оплату?** ЮKassa через Telegram: только `successful_payment`, с проверкой владельца, payload, RUB и суммы сохранённого заказа. Для имитатора — переход pending → succeeded на сервере. Оба пути вызывают один транзакционный обработчик. Возврат пользователя в интерфейс не подтверждает оплату.
3. **Что видит менеджер?** До оплаты — заказ «Ожидает оплаты» без поступления. После оплаты — ID платежа, одно поступление и сохранённую себестоимость. После подтверждённого возврата — возврат в журнале и пересчитанную сводку. Нажатие кнопки возврата не меняет показатели.
4. **Какие дополнительные расходы?** Доставка, упаковка, реклама, связь, прочие операционные расходы. Закупочная стоимость учитывается отдельно в себестоимости и повторно в расходы не записывается.
5. **Почему один бот?** Покупательский путь уже работает; один бот сохраняет заказы и общий сервер, не требует копирования данных или второго токена. Роль менеджера проверяется по разрешённому ID на сервере.

## Бизнес, роли и момент оформления

Покупатель готовится к поездке и выбирает рюкзаки, органайзеры, адаптеры, дорожные аксессуары и тревел-наборы. Для самовывоза нужны имя или псевдоним и пункт получения. Телефон и домашний адрес не собираются. Пункты «ул. Путешественников, 1» и «ТЦ Глобус» вымышлены.

Заказ оформлен после подтверждения и успешной транзакции SQLite: сохранены заказ и состав, корзина очищена, показан уникальный номер. Оплата — отдельный процесс. Менеджер видит новые и готовые заказы, меняет статус и управляет складом; покупатель получает уведомление. Владелец магазина получает финансовую сводку в том же менеджерском кабинете.

- Покупатель: каталог, фотографии, своя корзина, оплата, свои заказы, отмена до выдачи.
- Менеджер: те же функции, заказы в работе, склад, `/summary`, `/cabinet` и Mini App.
- Доступ к финансовому API: HMAC-проверка исходного `Telegram.WebApp.initData`, срок `auth_date` и ID из `MANAGER_IDS` на каждом запросе. Роль нельзя получить из текста сообщения, `initDataUnsafe` или ID в JSON-запросе.

## Запуск на чистом Windows

Установите Python 3.11+ и откройте PowerShell в папке проекта. Активация окружения не требуется.

```powershell
cd F:\web\expedition
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Только если `.env` ещё нет:

```powershell
Copy-Item .env.example .env
```

Не заменяйте уже заполненный `.env`. Откройте его в редакторе и заполните:

```dotenv
BOT_TOKEN=
MANAGER_IDS=
DATABASE_PATH=data/shop.db
YOOKASSA_PROVIDER_TOKEN=
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
MINI_APP_URL=
WEB_HOST=127.0.0.1
WEB_PORT=8080
INIT_DATA_TTL=3600
DEMO_PAYMENTS_ENABLED=true
RESERVE_SECONDS=120
```

`BOT_TOKEN` — токен существующего бота. `MANAGER_IDS` — ваш числовой Telegram ID; несколько ID разделяются запятыми. В `.env.example` секреты отсутствуют; `.env` и SQLite исключены из Git.

Запуск:

```powershell
.\.venv\Scripts\python.exe run.py
```

Каталог создаётся при первом запуске. Существующая SQLite мигрирует без удаления заказов. Перед первым обновлением при остановленном боте можно сделать локальную копию файла базы. Не запускайте два polling-процесса одного бота.

На macOS/Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env  # только при отсутствии .env
.venv/bin/python run.py
```

## Как открыть Mini App внутри Telegram

Пошаговая настройка ключей ЮKassa и временного HTTPS-туннеля — [docs/SETUP.md](docs/SETUP.md).

Кратко: запустите сервер командой выше; во втором терминале запустите cloudflared для `http://127.0.0.1:8080`; полученный HTTPS-адрес запишите в `MINI_APP_URL`, перезапустите только бота, затем `/start` или `/cabinet` под менеджером → «Финансовый кабинет». Туннель оставьте запущенным. Обычное открытие URL в браузере не даёт финансового доступа.

Не направляйте туннель на порт 8081: это отдельный тестовый стенд со временными данными, он не предназначен для публикации или защиты.

## Оплата и возвраты

**ЮKassa Test.** Токен провайдера из BotFather хранится в `YOOKASSA_PROVIDER_TOKEN`. Счёт берёт сумму из сохранённого заказа, в копейках. `pre_checkout_query` проверяет владельца, заказ, валюту, сумму и актуальность. Поступление появляется только после `successful_payment`; сохраняются оба charge ID.

Для полного возврата нужны `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` того же тестового магазина. Сервер проверяет GET платежа: `test=true`, статус succeeded, сумма и валюта. Затем создаёт возврат с устойчивым Idempotence-Key и отдельно проверяет его GET-запросом. Пока возврат pending или провайдер недоступен, сводка прежняя. Кнопка «Проверить у ЮKassa» продолжает незавершённую проверку после перезапуска. Только подтверждённый succeeded создаёт возврат в журнале.

**Имитатор.** Включён настройкой `DEMO_PAYMENTS_ENABLED=true`. Его способ оплаты подписан «Демонстрация без платёжного провайдера». Подтверждение заказа создаёт настоящий pending-платёж в SQLite. Покупатель завершает его учебной кнопкой succeeded или canceled. Успешный путь использует тот же транзакционный обработчик, что Telegram-платёж. Возврат проходит отдельно: сохранение задания → независимый вызов имитатора → подтверждение → запись журнала. Worker выполняет его автоматически; в Mini App есть «Повторить проверку возврата». До подтверждения итог прежний, но этот промежуток может быть коротким. В изолированных тестах worker управляется отдельно, чтобы проверить pending и ошибки.

**При получении.** Прежний путь сохранён. Такие заказы не считаются подтверждёнными денежными поступлениями автоматически: интеграции кассы или эквайринга на месте в проекте нет. Для демонстрации финансового задания выбирайте ЮKassa Test либо имитатор.

Покупатель отменяет только неоплаченный заказ: освобождается резерв. После принятой оплаты отмена отклоняется; менеджер запрашивает полный возврат. До подтверждения возврата склад и финансы не меняются. Возвраты автоматически продолжаются фоновым процессом; кнопка проверки позволяет выполнить попытку раньше.

## Формулы и даты

Все финансовые суммы, цены и себестоимости — целые копейки. Поля REAL старой схемы сохранены для совместимости; финансовые расчёты ими не пользуются.

```text
Денежный поток = поступления − подтверждённые возвраты − действующие расходы
Учебный результат = поступления − возвраты − себестоимость принятых продаж
                    + себестоимость полностью возвращённых товаров − расходы
```

В интерфейсе рядом с показателями указаны период и формулы. Поступления и возвраты выбираются по дате подтверждения на сервере, не по созданию заказа; даты периода включительны по Москве, в SQLite timestamps хранятся в UTC. Расход учитывается по дате, выбранной менеджером; отдельно хранится дата его ввода. Отмена/исправление расхода корректирует исходный период, история создания и изменения остаётся в журнале.

Возврат заказа прошлого месяца может дать отрицательный результат текущего. Это ожидаемая особенность выбранной учебной модели. Налоги и комиссии не моделируются.

## Общая база и миграция

- `users`, `products`, `cart_items`: исходные пользователи, ассортимент, корзины и остатки; у товара `price_kopecks` и `cost_kopecks`.
- `orders`, `order_items`: исходные номера заказов; итог в копейках, снимок цены и себестоимости каждой позиции, связь с товаром и резерв склада.
- `payments`: внутренний ID, заказ, провайдер, оба внешних ID, RUB, сумма, pending/succeeded/canceled и даты.
- `refunds`: один полный возврат на заказ, pending/succeeded/failed, ID провайдера и ключ повторного запроса.
- `finance_operations`: receipt/refund/expense, сумма, дата операции и записи, заказ, внешний ID события, автор, категория и описание; расходы физически не удаляются.
- `finance_audit`: создание, исправление и отмена расходов с автором и датой.
- `finance_notifications`: очередь уведомлений менеджеру с повтором при сетевой ошибке.

Индексы запрещают два успешных платежа и две операции receipt/refund одного типа на заказ. Смена статуса платежа и создание поступления выполняются в одной транзакции. Возврат и освобождение складского резерва также атомарны. Повтор события не удваивает финансовый результат или остаток.

Для старых оплаченных заказов с сохранёнными ID и `paid_at` поступления восстанавливаются с исходной датой. Прежнюю себестоимость восстановить нельзя: у старых позиций она NULL. Если такие операции входят в период, денежный поток показывается точно, учебный результат — «Не определён» с объяснением. Текущую себестоимость каталога задним числом не подставляем. Новые заказы всегда сохраняют снимок себестоимости.

## Склад и фотографии

Корзина не резервирует товар. При подтверждении сервер в одной транзакции проверяет доступность, списывает свободный остаток и сохраняет заказ. Последнюю единицу нельзя продать дважды. При отмене резерв возвращается один раз, при оплате повторно не списывается. Полный возврат предполагает пригодность товаров и возвращает их на склад, если это не было сделано при отмене. Автоматического истечения резервов нет.

У менеджера: `/start` → «Склад» → товар → −1/+1/+5/+10. У покупателя — одна кнопка «В корзину», количество меняется в корзине. Карточки используют локальные PNG; при отсутствии файла отображается текстовая карточка и предупреждение в терминале.

## Ограничения

Один магазин, RUB, тестовые деньги, полные возвраты. Частичные платежи, возвраты части заказа, налоговый учёт и автоматическая фискализация не реализованы. Если в ЮKassa включены чеки, потребуется отдельно настроить receipt и контакт покупателя. Неподтверждённые возвраты проверяются фоновым процессом и кнопкой менеджера; вебхуки возвратов не подключены. Уведомления об оплате сохраняются и повторяются при сбое; авария между отправкой Telegram и отметкой доставки может привести к повторному уведомлению, но не к повторному поступлению.

Mini App показывает последние 200 заказов и 500 операций выбранного периода; сводка считает все операции без этого ограничения. Изменение статуса выдачи — в боте. Для постоянной работы нужен стабильный HTTPS-хост; временный туннель предназначен для демонстрации. Тесты пройдены локально; живой возврат ЮKassa, открытие из Telegram по новому HTTPS-адресу и запись демонстрации требуют ваших ключей и ручной проверки.

## Запуск склада и восстановление

Правила SQLite основаны на [официальном описании BEGIN IMMEDIATE](https://www.sqlite.org/lang_transaction.html). Соединение ждёт блокировку до 1 секунды; начало перехода имеет до четырёх попыток с короткой задержкой. После исчерпания попыток клиент получает понятную ошибку и повторяет **тот же** request_id. Блокировка действует между процессами, mutex не обеспечивает корректность склада.

`reservations.state`: active → consumed / cancelled / expired. Состояние платежа независимо: pending / canceled → succeeded; запоздалый canceled не откатывает succeeded. Одна успешная оплата, одно поступление и один полный возврат защищены уникальными индексами. Ключ оформления уникален на покупателя; состав и параметры сохраняются в `checkout_requests`. Повтор ключа с другим составом отклоняется. Заказ, состав, резерв, journal, pending-платёж и очистка корзины фиксируются вместе.

`refunds` — постоянные задания с reason="sale" или "late", attempt_key, attempts, error, lease_until. Короткая аренда в БД распределяет попытки между процессами; один ключ провайдера предотвращает второй возврат при повторном вызове. Имитация провайдера имеет отдельную таблицу `demo_provider_refunds` в той же учебной SQLite и фиксирует свой ответ независимо от задания магазина. После потерянного ответа сначала читается результат существующей операции. Успех магазина и складской возврат фиксируются одной транзакцией.

Для ЮKassa после неоднозначного ответа сначала читается список возвратов платежа; известный ID проверяется GET-запросом. Ключ операции не меняется. [ЮKassa гарантирует идемпотентность 24 часа](https://yookassa.ru/developers/using-api/interaction-format#idempotence); после 23 часов неизвестного результата автоматическая повторная отправка прекращается и остаётся видимая ошибка сверки. Подтверждённый провайдером canceled тоже остаётся видимой проблемой. Новый ключ автоматически не создаётся. Живые запросы ЮKassa в этом прогоне не выполнялись.

`run.py` запускает `bot/inventory_worker.py` через lifecycle общего HTTP-сервера: проверка при старте, затем раз в 5 секунд. Освобождение резервов не ждёт медленного сетевого возврата. После обычного перезапуска успешная учебная операция возобновляется в пределах двух интервалов. Если провайдер недоступен, товар освобождается вовремя, а возврат остаётся pending с ошибкой и повторяется. Автор 0 в складском журнале обозначает автоматический переход сервера.

Наличная оплата прежнего магазина сохранена: при выдаче до истечения резерва менеджер потребляет резерв, но без отдельной кассовой интеграции финансовое поступление не выдумывается. Для проверки склада вместе с деньгами выбирайте имитатор или ЮKassa Test.

Перед первым запуском новой версии остановите прежний процесс и сделайте локальную копию рабочей SQLite. Затем обычный запуск применяет миграции без удаления данных:

```powershell
.\.venv\Scripts\python.exe run.py
```

На свежей базе откройте `/cabinet` → «Склад» → выберите товар → количество 10 → «Провести поступление». Получится **10 / 0 / 10**. В боте доступно показывается заново, сервер ещё раз проверяет все позиции при оформлении. В карточке заказа есть состав, сумма, срок и обновление. Отмена до оплаты освобождает резерв. На равенстве срока оплата уже поздняя, даже если кнопку нажали раньше.

## Изолированные проверки этапа 3

Одна команда запускает регрессионные тесты, 5 прогонов гонок на свежих данных, границы времени, ошибки и реальные остановки процессов:

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py
```

Параметры для защиты (не меньше пяти повторов):

```powershell
.\.venv\Scripts\python.exe scripts/check_warehouse.py --stock 2 --buyers 30 --repeat 5
```

Помимо заданных параметров всегда проверяются 10 единиц / 50 покупателей. HTTP-клиенты ждут общий стартовый барьер и обращаются к двум приложениям с независимыми подключениями к одному файлу SQLite. Каждый покупатель подписан отдельной учебной личностью и имеет свой ключ. Реальные initData, токены и рабочая база не используются; проверка подписи и ролей не отключается.

Отчёты: [warehouse-report.csv](docs/warehouse-report.csv) — сценарий → ожидалось → получено, [warehouse-report.json](docs/warehouse-report.json) — ответы HTTP, начальные параметры, ID, точные строки БД, журнал, суммы, победитель гонки и время восстановления; [warehouse-unit.log](docs/warehouse-unit.log) — полный вывод регрессионных тестов. Код завершения ненулевой при провале. После ошибки отдельного сценария набор печатает traceback и продолжает независимые проверки; итоговый код остаётся ненулевым. При ошибке подготовки не выполненные проверки явно отмечаются **не запускалось**; успешным считается только записанный passed. Набор не скрывает исключения. Результаты этого прогона и ограничения — [WAREHOUSE.md](docs/WAREHOUSE.md).

Каждая проверка создаёт новый `data/warehouse-tests/test-<сценарий>-<uuid>.db`. Эти файлы остаются локально для защиты, исключены из Git. Для ручного стенда:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_warehouse.py --db data/warehouse-tests/test-manual.db --stock 10 --buyers 20
.\.venv\Scripts\python.exe scripts/inspect_finance.py --db data/warehouse-tests/test-manual.db
```

Явный сброс **только указанной тестовой базы** при остановленном тестовом сервере:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_warehouse.py --db data/warehouse-tests/test-manual.db --stock 10 --buyers 20 --reset
```

Скрипт отклоняет пути вне `data/warehouse-tests/` и имена без `test-`; не использует DATABASE_PATH из `.env`. Подготовка создаёт схему, явное поступление и пользователей 1000..1019. Рабочую базу удалять не нужно.

Для ручного выбора точки остановки изолированного сервера (только loopback, отдельный учебный токен):

```powershell
.\.venv\Scripts\python.exe scripts/warehouse_server.py --db data/warehouse-tests/test-manual.db --stop after_late_commit
```

Вторая точка — `before_late_commit`; без `--stop` запускается восстановление. Запускаемый набор сам отправляет необходимые учебные запросы и сравнивает БД после завершения процесса с кодом 73/74. Управление временем, платежами и ошибками разрешено только объекту Database(training=True) в изолированных скриптах; `run.py` не регистрирует эти HTTP-маршруты.

Обычный Mini App получает только проверенные сервером данные. Все `/api/inventory*` доступны только менеджеру с подписанным initData. `/api/shop/orders*` проверяют подпись и владельца; сумму, роль и срок нельзя передать от клиента. Публичных маршрутов остановки процесса нет.


Пошаговая инструкция к пунктам приёмки 1–13, включая ручной Telegram-стенд и команды `--scenario N`: [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).
